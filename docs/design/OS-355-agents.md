# OS-355 Agents as an assignee type (design note)

Status: design for review. No code yet. Issue: OS-355. Size: L. The first slice is about M (2 to 3 days).

## Problem
`Issue.assignee` is free text, and the local MCP server (127.0.0.1, one bearer token) cannot tell which agent made a change. Everything is recorded as "MCP".

## Scope
First slice:
- Registered agents: Settings > Agents lists agents, each with a name, an icon or colour, its own MCP token, and a permission level.
- An assignee can be a person or an agent. The UI shows agents with a robot badge in pickers, cells, the board and filters.
- Every MCP call is authenticated by the agent's token, so changes are attributed to it in activity, the audit log (OS-351) and notifications ("Claude Code moved OS-12 to In Review").
- New MCP tools: `my_issues` (open issues assigned to the calling agent, with filters) and `whoami`.
- The existing shared token keeps working as an "Unnamed agent", so current setups don't break.

Deferred:
- Pushing work to agents (agents poll `my_issues`; webhooks from OS-356 can notify them later).
- Agent run status or logs inside Prometheus.
- Per-project agent scoping (this comes with OS-360).

## Data model and migration
```
Agent { id, name, color, level: 'read' | 'comment' | 'write', tokenHash: string, createdAt, revokedAt? }
Issue.assignee: string                     // unchanged; agents are stored as "agent:<id>"
ActivityEntry { ...; actor?: string }       // "me", "agent:<id>", or "sync:<deviceId>"
```
- `AppData.agents?: Agent[]` is optional, so there is no schema bump. Old assignee strings are unchanged.
- The `agent:` prefix keeps `assignee` a string, so filters, grouping and sync need no changes. Display looks the name up.

## Local-first and sync
- Agent rows sync, so a name shows the same on every device, but tokens are per device: only the token hash is stored in the row, and the plaintext token is shown once at creation.
- An agent registered on device A cannot call device B's MCP server until it gets a token on device B. That is intended.

## Safety (what agents may change)
- `read`: query tools only.
- `comment`: also add comments and change status on issues assigned to the agent.
- `write`: the current full tool set, apart from deletes, which require a `confirm: true` argument and are logged.
- Agents can never change settings, automations, agents, or sync.
- A per-agent rate limit (for example 60 writes a minute) guards against runaway loops, with a notification when it trips.

## UI touchpoints
Settings > Agents (create, copy the token once, revoke, set the level), assignee pickers, cells and board avatars, the "Assignee is agent" filter, activity lines, and notifications.

## Security
- Tokens: 32 random bytes, shown once. Only a SHA-256 hash is stored in data. Comparison uses `timingSafeEqual`, as now.
- The existing shared MCP token is stored in plain text in `userData/mcp.json` (file mode 0600). This change moves it into `safeStorage`, like the sync key.
- The server still binds to 127.0.0.1 only, with the Host-header check.

## Accounts or tokens Ashden needs
None. Agents get tokens generated by Prometheus. Ashden pastes them into each agent's MCP config, for example Claude Code's `.mcp.json`, kept out of any repo.

## Test plan
- Unit: resolving a token to an agent, attribution on each write tool, `my_issues` filtering, enforcement of the three levels, revocation, and the rate limit.
- MCP integration test: two agents with different tokens, each sees only its own `my_issues`.
- Smoke (xvfb): assign an issue to an agent and check the badge in list and board. Screenshot.

## Open questions for Ashden
1. Are three permission levels enough, or should agents be limited to particular projects from the start?
2. Should an agent be allowed to reassign issues to people or to other agents?
3. Which agents will you register first (Claude Code, Cursor, others)? That decides the setup instructions to write.

## Dependencies and suggested build order

Suggested order for the eight remaining features (each starts only after its design note is approved):

1. OS-353 Teams: no dependencies. Gives later features a stable "team" owner.
2. OS-354 Documents: project and space docs need nothing; team docs need OS-353.
3. OS-355 Agents as assignees: builds on the existing MCP server. Introduces the "actor" idea that OS-360 reuses for multiple users.
4. OS-356 Webhooks and local REST API: builds on the MCP tool layer. Introduces the shared credential store and the outgoing-HTTP delivery queue.
5. OS-357 Git integration: reuses the credential store from OS-356.
6. OS-358 Third-party integrations: reuses the credential store and delivery queue from OS-356, and the link model from OS-357.
7. OS-359 Cloud sync, single account first: one account syncing live across Ashden's devices. Its first slice needs no other feature (OS-353 and OS-355 data simply sync like any other rows), so it can be pulled earlier if live sync matters more. It introduces the backend.
8. OS-360 Multi-user collaboration and permissions: invites, accounts, guests, roles, presence, user pickers and enforcement. Needs OS-359 (server, op log, device auth) and OS-353 (team roles); uses OS-355's actor model for agents.

Items 1 to 6 keep Prometheus single-user and local-first. Item 7 adds an optional backend but stays single-user. Item 8 is where Prometheus becomes multi-user.
